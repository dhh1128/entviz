# Generic bech32 parser's HRP charset is [a-z], but BIP-173 permits chars 33-126 excluding uppercase — so a legal HRP containing '_' or a digit falls through to the base64url fallback with no scheme and no checksum verified

- 2026-08-05T00:06Z Surfaced 2026-08-04 while fixing the Cardano Shelley 29-byte hole (this.i:sh3lley29). BECH32_GENERIC_REGEX is ^([a-z]{1,83})1([bech32]{8,})$. BIP-173 allows HRP characters in the range 33-126 excluding uppercase, which includes digits, '_', '-' and more. Cardano's stake_test is the case that bit us — it missed BOTH the Cardano matcher (a length bug, now fixed) and the generic one, so it reached the base64url disproof fallback: no scheme, no checksum verified, rendered as a bare encoding. That failure mode is SILENT. Widening the charset is defensible on the [[g1tha5h0]] soundness bar because generic bech32 detection is checksum-gated (a random <letters>1<chars> string passes the polymod with probability ~2^-30), so admitting more HRP shapes does not make the detector guess. But it changes what parses — a spec-observable change needing its own version bump and corpus vectors — so it was deliberately left out of v17 rather than folded in. Decide it on its own.
