# Generic bech32 parser's HRP charset is [a-z], but BIP-173 permits chars 33-126 excluding uppercase — so a legal HRP containing '_' or a digit falls through to the base64url fallback with no scheme and no checksum verified

- 2026-08-05T00:06Z Surfaced 2026-08-04 while fixing the Cardano Shelley 29-byte hole (this.i:sh3lley29). BECH32_GENERIC_REGEX is ^([a-z]{1,83})1([bech32]{8,})$. BIP-173 allows HRP characters in the range 33-126 excluding uppercase, which includes digits, '_', '-' and more. Cardano's stake_test is the case that bit us — it missed BOTH the Cardano matcher (a length bug, now fixed) and the generic one, so it reached the base64url disproof fallback: no scheme, no checksum verified, rendered as a bare encoding. That failure mode is SILENT. Widening the charset is defensible on the [[g1tha5h0]] soundness bar because generic bech32 detection is checksum-gated (a random <letters>1<chars> string passes the polymod with probability ~2^-30), so admitting more HRP shapes does not make the detector guess. But it changes what parses — a spec-observable change needing its own version bump and corpus vectors — so it was deliberately left out of v17 rather than folded in. Decide it on its own.
- 2026-08-06T06:12Z 2026-08-06: investigating this found a LARGER, opposite-signed bug, and the two are the same fix.

THE BIGGER BUG — valid values are FALSELY REJECTED. BECH32_GENERIC_REGEX is ^([a-z]{1,83})1([bech32]{8,})$, and v14 made a structural match with a bad polymod REJECT the input outright rather than fall through. The v14 rationale says 'a <hrp>1<data> string with 8+ bech32 chars is a clear bech32 structural match'. That claim is FALSE. Measured on this box: 34 of 3000 random short hex strings (~1.1%) are refused outright with Bech32ChecksumError — e.g. 'dee1ad37cf96', 'a15c77a2f24e', 'c13a004ecf7d', 'd17cc6a6332658'. These are ordinary hex values that happen to contain a '1' with 8+ trailing characters that fall inside the bech32 alphabet. entviz simply will not render them. (Long digests are safe: 0 of 3000 sha256 hex digests hit it, because a 32+ char all-bech32-alphabet tail is unlikely.)

WHY THE TWO ARE ONE FIX. Widening the HRP charset to what BIP-173 actually permits (chars 33-126, splitting at the LAST '1' since the data alphabet excludes '1') is the fix for the original under-acceptance — but on its own it makes the false-reject problem WORSE, because more strings reach the bech32 path and get rejected. The reject rule has to be resolved first.

TWO WAYS, and this is a decision, not a detail — it reverses or amends a deliberate v14 rule and changes corpus vector err-cosmos-bad-checksum either way (so: v18 + a full release train).
  (A) RECOMMENDED. The GENERIC path falls through on checksum failure instead of rejecting; the PREFIXED schemes (bc1/tb1, ltc1, addr1/stake1, bitcoincash:/bchtest:) keep rejecting, because there the prefix IS a sound signal and v14's reasoning holds. Consequence: a corrupted cosmos-style address renders as a bare encoding rather than being refused. It is NOT silently accepted as an address — the label reads 'hex'/'base58'/'bech32', not 'bech32, cosmos1' — so the user still sees that recognition failed. Fixes the false rejects completely and makes the charset widening safe.
  (B) Keep rejecting, but raise the data-length floor from 8 to ~32 so the structural claim is actually true (real bech32 payloads are 20+ bytes = 32+ data chars; the corpus cosmos vector has 38). Cheaper, preserves v14, but only reduces the false rejects rather than eliminating them.
