# Two conformant implementations emit DIFFERENT DOM for the same >512-bit label: python writes the projected label as bare character data after the +hash tspan, entviz-js wraps it in a second tspan — neither Tier A nor Tier B catches it

- 2026-08-06T06:22Z Found 2026-08-06 by the agent implementing the entviz-js F1/F2 fix, and verified directly here. For render('0123456789abcdef'*16):
  PYTHON: <text ...><tspan fill="#a00000" font-weight="bold">+hash </tspan>hex, 1024-bit</text>
  JS:     <text ...><tspan fill="#a00000" font-weight="bold">+hash </tspan><tspan>hex, 1024-bit</tspan></text>
Same line, same raster, different DOM.

WHY IT SLIPPED THROUGH. Tier A compares the recovered render MODEL, not the serialization, so it never looks at this. Tier B strips text before rasterizing, so it never looks either. The spec's Conformance section claims to define 'the required SVG profile and paint order', but nothing in the corpus polices the text DOM — so the profile is normative in prose and unenforced in practice. That is the general gap; this label is one instance of it.

WHY IT NOW COSTS SOMETHING. entviz-js's F1/F2 fix makes an affirmative SVG verdict conditional on RE-RENDERING the value and comparing trees. A python-rendered >512-bit reference cannot be reproduced by the JS renderer, so it degrades from the green '≈' similar verdict to a plain 'unknown' and routes to the human walk. Correct behavior given the divergence, but real interop loss between two implementations that both certify as conformant.

TO DECIDE: which DOM is normative. The two candidates are python's (bare character data after the marker tspan — fewer nodes) and JS's (every run wrapped, uniform). Then say so in docs/spec.md's label-strip section, fix whichever port diverges, and consider whether Tier A should grow a serialization check so the SVG profile is actually enforced rather than asserted. Any of those is spec-observable, so it rides a version bump.
